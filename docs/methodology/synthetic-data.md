# Synthetic data foundation

Status: `IMPLEMENTED`, `TESTED` as of Milestone 2 — see
[../evidence/capability-status.md](../evidence/capability-status.md).

This is the one synthetic data foundation every pillar (M3 onward) and the
NexaMarket flagship build on. It is not a toy — every table is generated by
an explicit business process with deliberately encoded ground truth, so
later pillars can be validated against known answers rather than only
checked for "does it run."

## Reproduction

```bash
python -c "from decision_intelligence.data import build_synthetic_dataset; d = build_synthetic_dataset(); print({k: len(v) for k, v in d.tables.items()})"
```

or, to materialize a small committed sample under `data/samples/` and
`data/schemas/`:

```bash
python scripts/generate_synthetic_dataset.py
```

`build_synthetic_dataset(config)` with the same `config` (in particular the
same `seed`) always reproduces byte-identical tables — enforced by
`tests/integration/test_pipeline.py::test_rebuilding_with_the_same_config_is_byte_identical`.

## Entities

| Table                              | Represents                                             | Primary key                    |
| ----------------------------------- | -------------------------------------------------------- | -------------------------------- |
| `customers`                        | The NexaMarket customer population                      | `customer_id`                    |
| `products`                          | Subscription plans/catalogue                             | `product_id`                      |
| `marketing_campaigns`               | The one retention-offer campaign (M2 scope)              | `campaign_id`                     |
| `customer_treatments`               | Confounded assignment to that campaign                   | `customer_id`, `campaign_id`      |
| `customer_retention`                | Time-to-churn and the 90-day retention outcome           | `customer_id`                     |
| `subscriptions`                     | One subscription per customer, aligned to its churn      | `subscription_id`                 |
| `transactions`                      | Monthly billing events                                    | `transaction_id`                  |
| `experiment_assignments`            | The unconfounded recommendation-feature A/B test          | `customer_id`, `experiment_name`  |
| `experiment_outcomes`               | That experiment's conversion outcome                       | `customer_id`, `experiment_name`  |
| `sessions`                           | Customer browsing sessions                                 | `session_id`                      |
| `recommendation_exposures`          | What was shown (the impression log)                        | `exposure_id`                     |
| `events`                             | Click/purchase reactions to an exposure                     | `event_id`                        |
| `optimisation_reference_campaigns`  | A standalone, brute-force-solved budget problem             | `campaign_name`                   |

`latent_affinities` (per-customer affinity over product categories) is
generated alongside these but is **evaluation-only ground truth** — it must
never be used as a model feature; it exists so recommender evaluation
(M8/M9) has a known right answer to score against.

## Ground-truth design (Master Brief §16.3)

Four known facts are deliberately built into the generators, not estimated
after the fact:

1. **Experiment effect** (`experiments.py`) — assignment to the
   recommendation-feature test is an independent coin flip
   (`experiment_assignment_probability`, default 0.5) with a known
   absolute conversion lift (`experiment_true_effect`, default 0.04).
   Because assignment is unconfounded, a naive treated-vs-control
   comparison is an unbiased estimator of this effect in expectation.

2. **Marketing effect, deliberately confounded** (`marketing.py` +
   `retention.py`) — assignment to the retention offer is a logistic
   function of `latent_value`, the same hidden covariate that
   independently drives the baseline 90-day retention probability. A
   naive treated-vs-control comparison is therefore a *biased* estimator
   of `marketing_true_effect` (default 0.08) — overstating it, because
   higher-value customers are both more likely to be treated and more
   likely to retain regardless. This is the direct implementation of
   Master Brief §6.5: "a particularly important demonstration should show
   how an apparently significant observational relationship can disappear
   or change direction after appropriate causal adjustment." Recovering
   the true effect is left to Pillar 1 (M4/M5); M2 only guarantees the
   bias exists and is measurable
   (`tests/statistical/test_ground_truth_recovery.py::test_confounded_marketing_naive_estimate_is_biased`).

3. **Time-to-churn exactly consistent with a known probability**
   (`retention.py`) — each customer's true 90-day retention probability
   `p_i` (baseline, or baseline + the marketing effect if treated) is used
   to solve a per-customer Weibull scale such that `P(T_i > 90) == p_i`
   exactly. This gives two mutually consistent ground truths for the price
   of one: a clean probability-space effect for mean-difference estimators,
   and genuine time-to-event data with a per-segment hazard shape for
   survival analysis (M11).

4. **A brute-force-verified optimisation reference**
   (`optimisation_reference.py`) — 8 standalone campaigns, small enough
   that the true optimal budget-constrained selection is found by
   exhaustive enumeration (2⁸ = 256 subsets) inside the generator itself,
   independent of any solver. M12/M13 will check that Gurobi — and the
   HiGHS/SciPy fallback — actually reach this proven optimum.

## Confounding, exposure bias and data-quality failures (§16.2, §16.4)

- **Confounding**: see (2) above — `latent_value` drives both treatment
  assignment and the outcome.
- **Exposure bias** (`interactions.py`): item exposure is a mix of
  `"personalized"` (weighted by each customer's true category affinity)
  and `"popularity"` (Zipf-weighted, affinity-blind) selection. Popularity
  exposures are measurably more concentrated (higher Herfindahl index) than
  personalized ones — offline recommender evaluation (M8/M9) must account
  for this rather than mistake exposure frequency for true preference.
- **Missingness** (`quality.py`, applied in `pipeline.py`): configurable
  rates of null `household_income_proxy` and `region` on `customers`
  (defaults 5% and 2%).
- **Duplicate events**: a configurable fraction of `events` rows are
  duplicated with a fresh `event_id` but the same business key
  (`exposure_id`, `event_type`, `event_timestamp`) — exactly how a retried
  delivery would appear in a real log (default 1%).
- **Late-arriving data**: a configurable fraction of `events` rows have
  `recorded_at` delayed behind `event_timestamp` by 1–2 days (default 3%),
  for point-in-time correctness testing.

All rates live in `SyntheticDataConfig.quality` (`DataQualityConfig`).

## Reproducibility mechanism

`build_synthetic_dataset(config)` spawns one independent NumPy generator
per pipeline stage from `config.seed` via
`decision_intelligence.common.spawn_generators` (a
`numpy.random.SeedSequence(seed).spawn(n)`). This means adding, removing or
reordering an unrelated stage never changes another stage's random draws —
a property checked directly by the unit tests for each generator.

## Assumptions and limitations

- All entities are synthetic; no real customer data is used or implied.
- The 90-day retention window is evaluated against the *true* latent
  churn time regardless of whether the overall data horizon fully covers
  that window for customers who signed up very close to the horizon's end
  — a simplifying assumption, not a censoring-aware estimate.
- Only one marketing campaign and one experiment exist at this milestone;
  multiple concurrent campaigns/experiments and their interference are out
  of scope until the milestones that need them (M6/M7).
- `pricing_surveys`, `operational_capacity` and `costs` (listed as
  candidate tables in Master Brief §16.1) are not implemented yet — they
  are deferred to the milestones that actually consume them (M14, M12/M13)
  rather than scaffolded now with no content.
- The default build (`SyntheticDataConfig()`, 2000 customers) is the
  bounded size used by tests and CI. The committed sample under
  `data/samples/` uses a smaller, separate config (60 customers) purely to
  keep the repository lightweight — regenerate it with
  `scripts/generate_synthetic_dataset.py`.
